# Triage Drafts
A read-only planning routine that re-labels every draft task with a single priority prefix so the user can see, at a glance, what's worth approving and in what order. It **re-labels and reports — it never implements, cancels, or merges.** The user archives stale drafts themselves.
"Drafts" is the user-facing name for tasks in the `PROPOSED` state. Pull them with `listProjectTasks({ state: "PROPOSED", includeDescription: true })`.
## When It Runs
On "triage" / "triage drafts" / "re-triage" / "what should I do next", and naturally after heavy task churn so survivors get re-judged in the new context.
## The Single Question
Don't sort by *type* of work (test / perf / monitoring). Sort by one question for every draft:
> Is something broken, is this finishing/protecting an outcome that was already intended, or is this adding something new?
That collapses to the tiers:
- **[P0]** — broken now. Production down, data wrong, security hole. Drop everything.
- **[P1]** — will break, or a malfunction already exists (app still usable / workaround exists). e.g. a breached prompt-budget margin.
- **[P2]** — completes or protects an already-intended outcome, strictly in scope. Almost always advantageous to approve, and it does **not** add expansive new UI/capability.
- **[P3]** — adds new scope: net-new UI, new capability, new alert/automation, or polish.
- **[STALE]** — verification proves the symptom is gone; recommend archiving.
## The Two Rules That Keep P2 Honest
1. **The scope rule.** Any new UI element is **P3** — unless that exact UI was explicitly named in the originating task's "done looks like". Before anything with a panel/badge/alert can be P2, check the parent task's done-criteria. If the UI wasn't promised there, it's new scope → P3, however small or useful.
2. **Tests judged by blast radius.** A regression test is never automatically P2. It inherits the severity of the breakage it prevents: guards data integrity / report correctness / routing / another P0–P1 behavior → **P2**; guards something minor or cosmetic → **P3**.

## Workflow Each Run
1. **Pull all drafts** with descriptions (`listProjectTasks({ state: "PROPOSED", includeDescription: true })`). Cross-check against the latest task changes and fetch any just-created or missing ones — recent tasks may already have moved out of drafts.
2. **Verify "fix X" claims against live data before trusting them** — cheap read-only checks (see "Verification Before STALE"). If the symptom is already gone → STALE.
3. **Assign a tier** using the discriminator question, applying the scope rule for UI and the blast-radius rule for tests.
4. **Update only titles whose tier changed** — one prefix, never stacked, no noisy re-saves. Use `updateProjectTask({ taskRef, title })`. Strip any existing bracketed prefix before adding the new one so there is exactly one prefix per title.
5. **Report**, always leading with a ranked **Top 3–5 to approve next** (across tiers, P0/P1 first), then the buckets, count changes, and 2–3 observations (trends, clusters to batch, cheap wins).

## Title Prefix Mechanics
- Exactly **one** bracketed prefix per title: `[P0] `, `[P1] `, `[P2] `, `[P3] `, or `[STALE] `.
- Never stack prefixes. If a title already starts with one of these, replace it.
- Only call `updateProjectTask` when the tier actually changed — avoid noisy re-saves.
## Guardrails
- **Read-only.** Never implement, cancel, retire, or merge a task while triaging.
- **Verification before any STALE.**
- **Never expose internal state/tool names** to the user. Refer to PROPOSED tasks as "Drafts"; refer to tasks as `#N (Title)`. Do not mention `listProjectTasks`, `updateProjectTask`, `PROPOSED`, `PENDING`, etc.
- **Exactly one bracketed prefix per title.**

```markdown
- [STALE] (count): #N, ...
## Changes this run
- #N moved [old] → [new] (reason)
## Observations
- 2–3 trends, clusters worth batching, or cheap wins.
```
